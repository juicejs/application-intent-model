# Proposal (AIM 5.9) — A changed rule revisits what satisfies it

Status: **draft for review** · Author: Michael & Claude working session, 2026-09-27 · Affects: §16 (new §16.7, §16.6 amended), §1.2, §13 · Syntax: **none**

## The problem

`satisfies` makes "is this requirement realized?" a graph query (§8.2), and *Unrealized requirement*
(§12.2) reports a rule that nothing claims to realize. It checks that a claim **exists**, never that it
is **current**.

When an EXTEND rewrites a requirement, the units that satisfy it do not move, and the edge survives the
edit. The requirement still reads as realized, every check stays quiet, and the model now says two
things at once.

### Worked failure (FirePlanner review, 2026-09-19)

A fire-brigade duty-planning model had a rule that a draft is approved automatically once it is created,
and a step that sets the status to approved, carrying `[satisfies]` to that rule. The owner asked for
human approval instead. The Architect rewrote the rule and left the step, and the final checklist,
untouched. The label still resolved, the edge still pointed at the rule, and the graph reported a
healthy model: a rule forbidding automatic approval, satisfied by a step that approves automatically.

Why nothing saw it:

- **Unrealized requirement** — the edge exists, so it stays quiet.
- **Dangling reference** — the label still resolves.
- **§16.6** — "Intent Evolution adds no new diagnostics." True for transforms, which change addresses and
  never commitments (§16.3). A requirement edit is an EXTEND that changes a commitment, and §16 has no
  rule for that case.

Whether two prose sentences contradict each other is a judgment. Staleness is not: *this rule's text
changed, and this item that claims to realize it did not* is a fact about the diff, computable without
reading meaning.

## Scope sort (§1.4)

A requirement and the behavior that claims to satisfy it are one commitment — object-level, not meta.
The check needs the prior revision, like a transform's graph-diff (§16.4). It requires no particular
version-control environment (§1.3): any tool that holds both sides of a change — a proposal, a commit, a
change record — can compute it.

## Proposal

### 1. New §16.7

> ### 16.7 Changing A Commitment (5.9)
>
> A transform changes addresses, never commitments (§16.3). An EXTEND that rewrites a requirement
> changes a commitment, and it is unfinished until what realizes that commitment has been revisited. A
> `satisfies` edge claims that its unit is how the rule is kept, so the rule and each item carrying a
> `satisfies` edge to it — the list item, step or paragraph the token sits in — are one commitment: when
> the rule's text changes, each such item is either revised to keep the new rule, or kept deliberately
> because it still does.
>
> **Stale satisfier (5.9)** — computed over a change, never over a model at rest: a requirement whose
> text changed (the same label, or for an unlabeled item the same position) while an item carrying a
> `satisfies` edge to it did not change. The edge survived the edit, so the requirement still reads as
> realized and *Unrealized requirement* (§12.2) stays quiet. Rewording that leaves the commitment intact
> raises the same finding; the Architect confirms such an item rather than editing it for the sake of the
> check. Remediation: revise the item to keep the new rule. **Removing the `satisfies` edge is never the
> repair** — the behavior stays and only the claim disappears, so a visible contradiction becomes an
> unrealized requirement at best and a hidden contradiction at worst. Not reported: a newly added
> requirement (nothing points at it yet), a removed one (its edges dangle, §12.1), and reordered labeled
> items (a label is identity, §8.2).
>
> Any tool that holds both sides of a change — a proposal, a commit, a change record (§16.4) — can
> compute it; the spec requires nothing of the version-control environment (§1.3).

### 2. §16.6 — amend the opening sentence

Current: *"Intent Evolution adds **no new diagnostics**."*

Proposed:

> Intent Evolution adds **no new diagnostics** for transforms. [rest unchanged] An EXTEND that changes a
> commitment has one diagnostic of its own, the stale satisfier (§16.7).

### 3. §1.2 — Architect conduct (append to *Architect: validate before present*)

> A proposal that rewrites a requirement MUST also revisit every item that `satisfies` it (§16.7). A
> satisfier that still holds unchanged is kept and said so to the human, never silently.

## Against §8.6

A diagnostic and a conduct rule; tests 1 and 2 do not apply.

3. **Pays rent** — it catches a half-applied change that every existing check misses, with a
   deterministic test (text equality across the diff).
4. **Demonstrated need** — the FirePlanner review. The reference implementation reports it on every
   proposal (`server/src/propagation.js`, regression case in `server/test/propagation.test.js`).
5. **Fully specified** — keyed by label or position, "unchanged" means identical text, three exclusions.

## Migration (contribution to §13.10)

None. A diagnostic over change; no file changes.

## Decision needed

1. Admit §16.7, the §16.6 amendment and the Architect rule as proposed?
2. **Scope of "item":** list items only, or any line carrying a `satisfies` token, including a
   `### Summary` paragraph? The reference implementation checks bulleted items only, which misses
   numbered steps and paragraphs. In the shipped demo models 26 of 27 `satisfies` edges sit on bullets;
   in Amy's own self-model 76 of 347 do not. Recommended: any line, so the rule does not depend on
   where an author put the token.
3. MUST or SHOULD for the Architect rule?

## What this does not settle

- **Only `satisfies`.** The same shape exists elsewhere: a `### Decides` criterion rewritten while the
  outcome's continuation stays; a Contract's `### Ensures` rewritten while its bindings stay (that one is
  the Reviewer's drift loop already). No evidence yet for the others; `satisfies` is the relation where
  the spec can state it mechanically.
- **Detecting a change of meaning.** Not attempted. A reworded rule with the same meaning raises the same
  finding, which is why it is phrased as something the Architect confirms.
