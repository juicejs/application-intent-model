# Proposal (AIM 5.12) — Stated layout is intent

Status: **draft for review** · Author: Michael & Claude working session, 2026-10-18 · Affects: §7.5, §7.8, §9.4, §15.9, §13 · Syntax: **one optional sub-block, `### Layout`, on a View and in a Style; no new headings, edges or schema-line grammar**

## The problem

The reference implementation draws a layout draft of every screen. The owner looks at it and says
"the button should be on the left". Under 5.11 there is nowhere to put that sentence: §15.9 says
placement is realization, so the model cannot hold it, the next draft forgets it, the running
application never hears it, and a developer handed the model puts the button wherever they like.
That is the failure the generated mockups of 5.7–5.11 had at scale: the picture invented an
arrangement nobody committed to, and what the developer built was "terribly different" from it.

## The design

**The §1.4 test, applied to placement.** "The create action sits at the left, above the list" is a
commitment a Reviewer can hold any realization to. "A 12-column grid with a 24 px gutter" is how one
realization meets it. So the line falls where it fell for the look (5.11): what the owner states is
intent, at arrangement grain; everything unstated, and every mechanic below the grain, stays the
Realizer's freedom.

**Where it lives.** A View's `### Layout` — one bullet per arrangement commitment, in the owner's
words, naming what it places by the surface's own words (a Display section, an Action's label, a
Record it reads). Product-wide conventions ("actions always left-aligned") go in the Style's new
`### Layout` family, so one sentence covers every screen; a View's own bullet wins for that screen.

**Why not an edge, a grid, or positions.** Placement relates parts of one surface, not nodes of the
graph — §8.6's test 1 refuses it as a verb. A grid notation would be a stylesheet in disguise and
would fix the realization's freedom far below the owner's grain. Prose a Reviewer judges is the
same choice `### Display` made, and the same as Style's words.

**A drafted arrangement is not a layout.** A tool that draws a screen has to arrange what the model
leaves open. That arrangement is a suggestion: never written into `### Layout` unasked, and a draft
SHOULD show which placements the model states and which it chose. The owner's reaction is an
ordinary change, after which every reader — the next draft, the running application, a developer —
places it the same way.

## Migration

Additive; nothing becomes invalid. A placement already stated in `### Display` prose may stay;
tools SHOULD offer to move it into `### Layout` when the View is next edited.
