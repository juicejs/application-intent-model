# Proposal (AIM 5.6) — External information: the source is a commitment

Status: **draft for review** · Author: Michael & Claude working session, 2026-07-30 · Affects: §8.2, §9.2, §9.3, §12.2, §15

## The problem

An intent can now be **performed**: exported as a prompt and executed by an agent (§1.2's
performance realization — the reference implementation ships exactly this: an Operate-mode export
claimed by a local orchestrator). A performing agent routinely needs **information from outside
the system** — a registry, a feed, a document, a person. The language has no working way to say
so, and the failure is already observable in practice.

**Worked failure — the Weather Monitor.** Narration: *fetch the current local weather every two
minutes; write STATUS.txt; on an active warning, write WARNING.txt.* The Architect produced a
model that passes every current diagnostic: a schedule Trigger, an orchestrating Flow, `FetchWeather`
and output-writing Contracts, fetched/failed Events, config and output Records. And yet **the
weather source does not exist in the model.** The process's entire purpose is consuming external
information, and the model carries no node saying what kind of source that is:

- The performer must **invent** the source at run time — and for the warnings file that is not a
  detail: weather warnings are the pronouncements of an official alerting authority, and "warnings
  originate from an official source" is a commitment a Reviewer should be able to hold a
  performance to. Two conforming performers may ground the same obligation in different
  information — the exact per-execution divergence the 5.5 step semantics were added to prevent.
- A **pre-flight manifest** ("what must be provided for this intent to run?") is derivable from
  the graph today for config inputs and schedules — but it reads *complete* while silently missing
  the source. That is §15.10's false-assurance failure resurfacing at the orchestration layer.
- The Architect never asked where the information comes from — elicitation guidance has no source
  question — but this is not only an elicitation gap: **had she asked, the language gives her no
  good way to write the answer down** (see below).

**Scope sort (§1.4).** The *informational basis* of an operation is a commitment — "grounded in
the sub-ledgers and the bank statements", "an official weather source, current conditions and
warnings, per city". The *concrete provider* is not (mapping/binding territory), and *access
mechanics* — credentials, transport, vendor API shape — are realization, never modeled. The
language already has this three-layer split: **Capability (§9.2) = the kind; mapping (§9.3) or
binding (§10.2) = the source; mechanics = realization.**

## Non-goal: a `## Source:` facet

The instinct that external information deserves its own facet is right about the *need* and wrong
about the *node*. External information decomposes into four shapes the taxonomy already carries:
pull-queryable (**Capability**), push-arriving (**Trigger** → ingest → Record), materialized at
rest (**Record**), and human (**Persona** behind `### Authz`). A `Source` facet would reclassify
these by origin without adding a commitment they cannot carry — and it has no lifecycle of its
own: a source with substance is just the provider modeled as an intent, a form that already
exists. It fails the admission tests the way `performs` failed them (§8.6): expressible today.

What is *not* expressible today is narrower, and it is the actual gap. **The Capability facet is
crippled twice:**

1. **It is not a legal edge target.** `invokes` reaches `contract | flow` only (§8.2), so an
   operation cannot declare "I consult this source-kind" in the graph. For a *mapped* capability
   the use site points at the resolved provider's contract; for an **unmapped external** capability
   there is no node to point at, at all. The basis of a judgment is unstatable exactly in the
   performed-intent case.
2. **Its resolution is too rigid for external sources.** "Unresolved `Requires` aliases are hard
   errors" (§9.3) forces every genuinely external source — a bank feed, a public registry, a
   weather service — to masquerade as a modeled provider intent, or the model does not validate.

So: no new facet. Repair the one that exists.

## Proposal 1 — Capability is the information-source surface (§9.2, doctrine)

A `## Capability:` block declares any required external surface: an invocable **service** *or an
information **source***. The surface's Summary/Operations state the **kind** — which is the
commitment — never the vendor:

````markdown
## Capability: WeatherSource

### Summary

An official weather source: current conditions and active warnings, queryable per city.

### Operations

- `CurrentConditions(city) -> Conditions`
- `ActiveWarnings(city) -> Warning[]`
````

Declared as today via `## Dependencies → Requires: WeatherSource`. For document-shaped
information, the doctrine stays **acquisition-as-step**: a collect Contract consults the
capability and materializes a Record; downstream operations `read` the Record — the basis remains
graph-derivable end to end.

## Proposal 2 — `invokes` may target a Capability (§8.2, additive)

The `invokes` to-set gains `capability` (from-set unchanged; no new verb):

```markdown
- Fetch current conditions and warnings — [invokes](aim:#Capability:WeatherSource)
```

- **Meaning:** the acting unit *consults this source-kind*. Inside a `### Steps` item the token is
  the step's operation exactly as any `invokes` (§7.3); joint/exclusive semantics unchanged.
- **No derived inverse.** `triggered-by` derives only for `invokes` edges whose target is a
  Contract or Flow; a capability is a surface being consulted, not a behavioral unit being
  entered. Stated explicitly per §8.6 test 5.
- **Orphan semantics:** a Capability with no inbound `invokes` and no `Requires` alias is
  declarable-but-unused — informational, mirroring the unused-import reading.

## Proposal 3 — External resolution: mapping *or* binding (§9.3)

A `Requires` alias resolves through **either** of two forms:

- a **mapping** (`## Map:`, §9.3) — the provider is a modeled intent (intent→intent, unchanged);
- a **`### Bindings` property on the `## Capability:` surface itself** (§10.2 — `system:`,
  `agent:`, or another locator): the provider is an external system. The **kind stays intent; the
  where is realization**, provenance-stamped like every binding, so it can go stale without the
  commitment being wrong (§1.3).

Unresolved by *either* remains a hard error at validation time — the softening admits the external
form; it does not weaken the rule that a required capability must be accounted for.

## Proposal 4 — Ungrounded-decision diagnostic (§12.2, informational)

A `### Decides` block on a unit that declares no informational inputs — no `reads`, no
capability-targeted `invokes`, no `### Input` — is a **judgment with no stated basis**: nothing in
the model says what the decision is decided *from*. Informational; remediation is to declare the
basis (a Record read, a Capability consulted) or accept that the criteria are self-contained.

## Proposal 5 — Authoring doctrine (§15 + brains)

An operation that acquires information from outside the system **declares the Capability it
consults** — the source stays visible as an edge, never implicit in a fetch-contract's prose.
`FetchWeather` with no capability edge is the canonical miss. (Elicitation side, for tooling: when
narration fetches/looks up/checks/monitors the outside world, ask what *kind* of source — never
which vendor.)

## What the graph gains

- **The basis is queryable.** "What does this judgment consult?" and "which operations depend on
  this source-kind?" become graph queries; impact of changing a source is an impact set.
- **The pre-flight manifest becomes complete.** Required inputs of a performed intent derive from
  the graph: unresolved capabilities + input Records (read but never mutated in-model) + schedules
  to arm + personas to reach. Today that manifest silently omits the source; with the edge, the
  Weather Monitor manifest reads: *provide a city; provision an official weather source; arm the
  two-minute schedule.*
- **Exported prompts can say what to connect.** Resolved → "use provider X"; bound → "connect to
  the bound system"; unprovided → "the operator must provision a source of this kind."
- **Ungrounded judgments surface** instead of hiding behind well-formed criteria prose.

## Open questions for review

1. **Prose-shaped Operations.** For information sources, must `### Operations` carry signatures,
   or is a prose line ("provides current conditions and warnings per city") enough at Level 1/2?
   Drafted above with signatures; relaxation is a one-line follow-up if authoring friction shows.
2. **`reads` and capabilities.** Consulting is modeled as `invokes` (an act). Is there a real case
   for `reads` → capability (passive dependence), or does acquisition-as-step cover it? Proposed:
   keep `reads` record-only.
3. **Acquiring-contract-without-basis.** Should a fetch-shaped Contract with no capability edge be
   its own informational diagnostic, or does that stay elicitation-side (lens) to avoid noise on
   models whose sources are internal? Proposed: elicitation-side for now; revisit on evidence.
4. **Resolution path for capability addresses (§11).** `#Capability:X` resolves within the
   declaring intent today; confirm upward resolution follows §11.1 unchanged for cross-intent
   references to a shared capability surface.
5. **Per-operation bindings (from review, 2026-07-30).** An external database source ("the ERP's
   `customers.credit_limit`") wants site precision below the surface:
   `- binds: \`table:erp.customers#credit_limit\` — as: CreditLimit` — the existing binding grammar
   (`— as:` naming what the site realizes) already permits this, making it the external analogue
   of §9.3's Operation Map. Should §9.3 document the pattern in one sentence, or stay silent and
   let the open locator scheme carry it? (The column stays realization either way; the operation
   stays the commitment. Query mechanics and credentials remain orchestrator-side, never modeled.)
   — *Resolved in review (2026-07-30): documented, one sentence in §9.3.*
