# Proposal (AIM 5.7) — Supplied material: the words are owed, the words are not intent

Status: **draft for review** · Author: Michael & Claude working session, 2026-08-12 · Affects: §7.5, §9 (new §9.4), §12.2, §13

## The problem

A model can be **structurally complete and still unbuildable**. This is not a hypothetical: it is
the most-reported failure from people using the reference implementation on websites and product
UIs. They model the structure — intents, personas, flows, screens, the records each screen reads —
and it works. They hand the export to a developer. The developer stops, because the model does not
say a single word the product actually displays.

**Worked failure — the marketing site.** Narration: *a landing page, a pricing page, an FAQ; a
visitor reads them and requests a demo.* The Architect produces a model that passes every current
diagnostic and reaches Level 3: Personas with `accesses`, Views with `### Display` and `### Actions`,
a `RequestDemo` Contract that `mutates` a `DemoRequest` Record, an `FaqEntry` Record the FAQ view
`reads`. Nothing dangles; nothing is unreachable; every requirement has a `satisfies`. And the
realization cannot be built:

- **No headline, no body copy, no empty states.** `### Display` says *"an empty state message if no
  tasks exist"* — the prose commits that an empty state exists, and stops exactly where the words
  begin. The only authored words that reach a developer are `### Actions` labels.
- **No FAQ entries.** `FaqEntry` is read by a View and mutated by nothing in the model. §9.2 already
  names that category — "Records read but never mutated in-model" — as part of the graph's statement
  of *what must be provided for this to run*. The graph identifies the hole and the language cannot
  fill it.
- **The Realizer is forbidden to improvise.** §1.2: *"The Realizer must not invent material behavior
  absent from intent."* A conforming Developer's only conforming move is to stop and ask. So the
  handoff stalls **by design** — which is correct, and is precisely why the language owes an answer.
- **Worse: it stalls silently in the good case and ships in the bad one.** A tool that renders
  plausible mock copy (the reference implementation does) shows the owner a finished-looking screen
  whose words evaporate at export. That is §15.10's false assurance, one layer further out.

The 5.6 proposal's own sentence transfers almost verbatim: the Architect never asked what the screen
says — elicitation guidance has no content question — **but had she asked, the language gives her no
good way to write the answer down.**

## Scope sort (§1.4)

Run the standing test — *is X a commitment a Reviewer can hold a realization accountable to, or is
it how a realization meets one?* — and content splits cleanly in two, along a line the graph already
draws:

- **That material is owed is a commitment, and it is *derived*, not authored.** A View that `reads` a
  Record commits to displaying that data, so it owes the reader something when there is none. A
  Record read but never mutated in-model commits to having starting contents that come from outside.
  Both are graph facts today. No new authoring.
- **The material itself is realization.** "Your work, in one place" is not a commitment about
  behavior; it is one way of meeting the commitment that this screen says what it is for. The exact
  string, the exact FAQ rows, the exact hero image — these are the Realizer's or the owner's to
  supply, exactly as an endpoint or a credential is.

This is the **same three-layer split 5.6 landed**, one column over:

| | kind / obligation (intent) | the concrete thing (supplied) | mechanics (realization) |
|---|---|---|---|
| 5.6 external information | `## Capability:` — the source-kind | mapping / binding — the provider | transport, credentials |
| 5.7 supplied material | the graph — *this screen owes copy; this record owes rows* | the supplied values — the words, the rows, the assets | typography, layout, CMS |

And it keeps §15.9 intact: **nothing here re-admits layout.** Where the headline sits is still
realization. This proposal is about whether the headline *exists anywhere at all*.

## Non-goal: a `## Content:` facet or a `### Copy` block

The instinct that content deserves its own facet is right about the need and wrong about the node —
the same way `## Source:` was in 5.6. Run §8.6's admission tests on a `### Copy` block:

1. **Not a relational commitment.** A string is an attribute, and §8.6 test 1 sends attributes to
   `schema`. But a Record's schema declares *types, never values* — `default(...)` and `enum(...)` are
   the only literals the language admits, and neither is instance data. Content is not a relation and
   not a type, so it is not a graph node in any position.
2. **It would create a second authority over the same words.** `### Actions` labels are already the
   author's words, in intent, where they belong: an action label *names a commitment*. Add a copy
   block and every button has two homes — the §1.3 authority model's worst case, and the exact
   failure the mapping/binding distinction exists to avoid.
3. **It would make intent churn on taste.** A headline is rewritten five times before launch. Under
   intent authority each rewrite is a model change, a diff, a change record, a re-review — review
   cost with no review value. §1.4's warning applies directly: formalizing this "would consume the
   degree of freedom that makes a realization the Realizer's to choose."
4. **It is already expressible.** §10.2 says the binding scheme set is **open**, and that *"unknown
   schemes are valid; a tool that cannot check a scheme reports the binding as unverifiable, never as
   an error."* A supplied-material channel needs no new syntax — only a name, a convention, and a
   diagnostic.

So 5.7 **admits no verb, no facet, and no authored block.** It is the smallest wave in the language's
history: it names a derived category, states a conduct rule, and defines the handoff channel.

## What it does admit

1. **A name for the category (new §9.4).** *Supplied material*: the concrete displayable values a
   realization needs and the model deliberately does not state — screen copy, seed entries for input
   Records, media. Derived need, supplied values, never written into `.aim`.
2. **A conventional channel.** `records/<Name>/seed.json` and `content/` in a handoff bundle. This is
   not new ground: §9.2's manifest sentence already sends provided values to `records/<Name>/`, and
   the reference implementation's Operate role already keeps records there. 5.7 writes the convention
   down so a *third-party* implementer agent — one that never saw this tool — knows where to look and
   knows the values are realization.
3. **Two advisory diagnostics (§12.2).** *Unsupplied material*: a View whose derived copy is absent, a
   Record read-but-never-mutated with no supplied rows. Informational, never a validation error —
   material is a handoff-readiness fact, not a model defect. This is the rent §8.6 test 3 asks for:
   *"this screen will render empty"* becomes computable, and the false-complete manifest of the
   worked failure above stops reading complete.

## Why the authority model forces the channel to be named

§1.3 is the reason this cannot be left as a tooling detail. Content parked in a `docs/` folder or a
loose JSON blob outside the authority chain is **invisible to authority** — it drifts against the
model with nothing able to notice. Naming the channel, and stating that its values are realization
that must never be written back into intent, is what keeps a filled-in screen from quietly becoming
a model change. The rule is one sentence, and it is the whole point: **use the material verbatim;
never write it back.**

## What this does not settle

- **Per-persona or localized variants.** A screen with copy per audience is plausibly a real
  commitment ("the admin sees a different framing"), but there is no evidence for it yet, and §8.6
  test 4 admits from evidence, never anticipation. Out of scope.
- **Where a slot list comes from.** Deliberately unspecified, as with the realized-graph manifest
  (§10.1) and the change record (§16.4): *which* slots a screen owes is an ecosystem concern. The
  spec says material is owed and derived; it does not standardize the derivation.
- **Whether a Record that IS content should be modeled at all.** An `FaqEntry` with a schema is a
  Record; that stays true. 5.7 only says its starting rows are supplied, not authored.
